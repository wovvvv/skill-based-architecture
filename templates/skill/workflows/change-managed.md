# Change-Managed Workflow

Use this for non-bug changes whose partial edits can drift: features, refactors, generated/copied files, shared configuration, or changes with derived targets. A feature or any request that adds or changes user-visible behavior, a business flow/state, or an external contract is Managed even when it sounds local: complete Requirement Definition, let [`task-execution.md`](task-execution.md) project its Task Anchor, bind the implementation through Steps 1-3, and only after `implementation-ready` derive the Native Plan before mutation. Other non-Simple changes use the same handoff; this workflow remains authoritative for domain order. Use [`subagent-auxiliary.md`](subagent-auxiliary.md) only for one admitted auxiliary workstream and [`refactor-fanout.md`](refactor-fanout.md) only for several independent usage batches.

Start without domain knowledge. An explicit business-rule request or a governing Requirement/Plan that already declares the applicable business-domain owner may activate `domain-routing.yaml` immediately after this workflow is selected; otherwise inspect the smallest source slice first and activate one domain only when an unresolved business decision appears. Read the governing Requirement and any consuming Plan directly; their existence alone does not activate a domain. Keywords alone do not activate a domain. Before the first mutation, read [`change-discipline.md`](../rules/change-discipline.md).

For a requirement-bearing behavior/contract change, always evaluate [`change-contract.md`](../protocol-blocks/change-contract.md). A clear source Requirement or explicit request may satisfy `requirement-ready` with zero questions; otherwise enter [`define-requirement.md`](define-requirement.md) internally and return only the minimum normative question. Never ask the user to re-route. Once ready, establish the Task Anchor and consume [`source-localization.md`](../protocol-blocks/source-localization.md). Steps 1-3 must bind the returned owner, Current -> Target, affected path, high-cost boundaries, and proof obligations. Only then mark `implementation-ready`, derive the Native Plan from Steps 4-9, and permit mutation. For fixed-contract refactors or generated/copied changes, activate the contract only when desired outcome, authority, preservation, scope, or acceptance is not already fixed.

## Steps

1. **Replay the Requirement and bound the owner region** — carry its Goal, acceptance, material Boundaries, authority, and preserved behavior through the Task Anchor without rewriting them. Name candidate modules only as implementation hypotheses. For business-bearing work, read the routed business model when evidence activates it. Record `business-model impact: unchanged / proposed change / unknown`; a proposed type/flow/state/boundary/invariant change returns to Requirement Definition.
2. **Find the source of truth and owner** — distinguish canonical content/state from generated, copied, or downstream consumers; trace provenance and the producer-to-consumer call chain.
3. **Map semantic fan-out** — name the invariant and list every affected full/incremental/read/write path, derived target, registration, test, and doc/index that must stay synchronized.
4. **Choose the technical design and owning boundary** — consume or produce the fitted Implementation Plan. Default to Product Development and make every coordinated change needed for semantic completeness. Operational Stabilization requires an explicit production/availability/frozen-scope constraint and must expose unresolved structural work.
5. **Make the smallest semantically complete change** — use minimality only to choose among complete solutions; preserve unrelated edits and avoid adjacent cleanup.
6. **Sync derived files** with the owning generator/copy process.
7. **Check drift** across all mapped targets, semantic paths, the user-confirmed Requirement mainline, and the Plan's technical decisions. If current or in-progress implementation diverges from desired meaning, invoke [`task-execution.md` § User Decision Drift Gate](task-execution.md#user-decision-drift-gate) immediately: pause the affected path, expose the gap/constraints/cost/risk, and obtain a user decision before continuing. If only a technical premise changes, rebind and revise the Plan. Do not silently fit the Requirement to existing code or wait until review/Closure.
8. **Validate behavior** with the cheapest sufficient fresh evidence; escalate only when concrete runtime/release risk requires it.
9. **Run [Task Closure](task-closure.md)** once after the integrated change.

If templates, scaffolds, entry shells, or reusable project structure change, also follow [`edit-templates.md`](edit-templates.md). If this project has already activated an operation-permission model, apply its pre-operation classifier and closure check; the default scaffold assumes none.

## Completion Check

Scope, governing Requirement/mainline, applicable Plan technical decisions, any activated Change Contract, invariant, ownership/provenance, call chain, all semantic paths, fan-out targets, sync, resolved drift, targeted validation, and Task Closure are all accounted for without copying the complete shared protocols here.
