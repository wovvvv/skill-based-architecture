# Composite Plan Execution

Load this protocol only when one outcome governed by a common Requirement projection consumes technical work from multiple independently maintained Component Plans. It owns composition intake and technical execution handoff; `task-execution.md` remains the continuity kernel.

## Intake

1. Identify the common governing Requirement projection and one truthful Integrating technical owner. Task Execution alone projects that Requirement into one Integrating Task Anchor. A durable Integrating Plan is required only when composition has its own handoff, technical conflict, authorization, recovery, integrated-proof, or Closure pressure.
2. For each Component, read its governing Requirement or Requirement projection for Goal, meaning, invariant, boundary, and acceptance. Read its Component Plan only for technical decisions, implementation interfaces/adapters, risk, proof, ordering, and delivery mechanics. Never mirror Component content or live status.
3. Classify each input: `done` is frozen; authorized `executing` work enters the Integrating Native Plan; an included `draft` must close its load-bearing interface and enter execution; missing, `abandoned`, replaced, or unauthorized inputs block or leave scope.

## Return Ownership

- A Goal, meaning, invariant, boundary, permission, or acceptance conflict returns to Requirement Definition and the affected Requirement owner.
- A technical interface, adapter, ordering, risk, proof, or delivery conflict returns to the affected Component Plan or Integrating Plan owner.
- Conflict with user-confirmed meaning also invokes [`user-decision-drift.md`](user-decision-drift.md); a frozen Component Plan changes only through a technical successor that the Integrating Plan then consumes.

## Handoff Result

Return exactly one result to Task Execution:

- `ready`: the Requirement projections are compatible and technical integration is ready for Task Execution to derive one Integrating Native Plan under the already-projected Integrating Task Anchor; this protocol neither creates that Anchor nor defines the common outcome or integrated acceptance;
- `blocked`: name the invalid/missing Component and required owner action;
- `requirement-return` or `design-return`: name the unresolved normative or technical decision and its owner.

Components never create competing runtime anchors, step stores, or semantic `Current Task` entries. Session-only composition creates no durable graph artifact.
