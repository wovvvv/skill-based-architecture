# Composite Plan Execution

Load this protocol only when one outcome consumes multiple independently authoritative Plans. It owns composition intake and execution handoff; `task-execution.md` remains the continuity kernel.

## Intake

1. Identify one truthful Integrating owner. A durable Integrating Plan is required only when composition has its own handoff, conflict, authorization, recovery, integrated-proof, or Closure pressure.
2. Read each Component from its canonical owner and consume only its current decisions, boundaries, interface, local acceptance, and proof. Never mirror Component content or live status.
3. Classify each input: `done` is frozen; authorized `executing` work enters the Integrating Native Plan; an included `draft` must close its load-bearing interface and enter execution; missing, `abandoned`, replaced, or unauthorized inputs block or leave scope.

## Return Ownership

- Order, legal adapter, integrated proof, or delivery conflict returns to the Integrating owner.
- Component meaning, invariant, boundary, accepted interface, or local acceptance returns to that Component's Design owner.
- Conflict with user-confirmed meaning also invokes [`user-decision-drift.md`](user-decision-drift.md); a frozen Component changes only through a successor that the Integrating owner then consumes.

## Handoff Result

Return exactly one result to Task Execution:

- `ready`: one Integrating Task Anchor and one Native Plan cover the common outcome and integrated acceptance;
- `blocked`: name the invalid/missing Component and required owner action;
- `design-return`: name the unresolved interface or authority decision.

Components never create competing runtime anchors, step stores, or semantic `Current Task` entries. Session-only composition creates no durable graph artifact.
