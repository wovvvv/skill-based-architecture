# Plan And Knowledge Closure

Load this protocol only for Design-derived, business-bearing, knowledge-changing, or Composite Plan work. It returns reconciliation evidence to `task-closure.md`; it cannot declare readiness or completion.

## Reconciliation

1. For Composite work, enumerate every one-way `consumes` edge from the Integrating Plan and read each Component from its canonical owner. Reject missing, `abandoned`, unresolved-Delta, superseded-but-consumed, or unfinished required inputs. A `done` Component is frozen; no required Component may remain `draft` or `executing`; a true `subplan_of` shares its parent's lifecycle, while an independent Component retains its own lifecycle. Reconcile each affected Component's Decision Delta, local acceptance, fresh proof, delivery responsibility, and durable distillation before integrated acceptance; abandoning the Integrating Plan never changes independent Component state.
2. Replay each relevant user-confirmed Requirement Decision Context. For business-bearing work, read the routed business rule and compare `desired business truth` with code/tests/runtime `current implementation fact`. Material drift returns to [`user-decision-drift.md`](user-decision-drift.md); Closure never resolves it.
3. Reconcile later Requirement Decision Deltas across the governing Requirement, consuming Plan, Component interfaces, Task Anchor, implementation evidence, tests, and business owner. Preserve authority and mark replaced meaning explicitly.
4. Run Plan Leaf Reconciliation before implementation handoff, then verify that handoff here. Requirement Definition and Business Truth must have written confirmed durable business meaning through the unique owner; `plan-feature.md` must preserve one-way Requirement Provenance, consume rather than redefine that meaning, and initialize truthful `distilled_to:` targets. Closure verifies that the normal activation path changes a future action and returns missing handoff work to its owner; it is not the first place to compress or write the user-confirmed mainline. Reconcile only later Decision Deltas here.
5. Run Knowledge Reciprocity for changed rules, Gotchas, references, or workflows: integrate/correct/retire the existing concept, prove owner and activation, and avoid transcript copies or parallel truth.
6. Prove the Integrating Plan's consumed interfaces, common outcome, integrated acceptance, and delivery responsibility after Component reconciliation. Calibrate `distilled_to:` to current live semantic destinations and durable distillation owners. Do not list generated consumers, implementation-only files, rejected candidates, or nonexistent targets.

## Return

Return exactly one result: `pass` with owner/proof paths; `return` with the Task Execution or Rule Update action still required; or `blocked` with the missing authority/Component. Abandoning an Integrating Plan never changes independent Component state.

Rationalization to reject: “I can mention mainline drift in the final report.” First disclosure at Closure is too late; return to the drift owner immediately.
