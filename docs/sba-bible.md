# SBA Bible：产品信念与发展方向

这份文档定义 SBA **应该成为什么**，用于判断产品方向、架构取舍和新机制是否值得进入。它不是当前功能清单，不替代代码、测试、工作流或具体计划，也不要求普通任务每次读取。

## 产品边界

> SBA 就是一个 Skill，不是 Agent 操作系统，也不是任务、状态或执行平台。

SBA 通过规则、路由、业务语义和工作流，帮助当前 Agent 更可靠地使用所在 harness 已有的 Plan、Subagent 和工具能力。某个 harness 缺少能力时，SBA 应当优雅降级；它不自建常驻服务、任务数据库、统一状态机或独立调度 runtime 来补齐平台能力。

## 最高纲领

> SBA 的目标不是让每个人学会设计 Skill，而是让普通项目成员把仓库拉下来后，Agent 就能在真实项目规则、业务语义和验证契约下可靠工作。所有能够由 SBA 作者和机制吸收的复杂度，都不应转嫁给普通使用者。

SBA 的价值不在于让 Agent 做更多动作、维护更多文件或经过更多流程，而在于提升它面对真实项目时的判断力、协调力和结果能力。

> 真正的提效不是 AI 代替人敲代码，而是 AI 能够自己完成“产品语义 → 可执行变更契约 → 当前代码 owner”的翻译；人只在规范性含义、权限边界和高代价取舍这些硬关卡上决策。

## 要证明的三件事

> 要做的不是让你变得更忙，而是要让我看到你能不能做到三件事：你能不能看到更完整的信息；你能不能在没有标准答案的时候做判断；你能不能让别人按照你的意愿做事情。

### 1. 看到更完整的信息

“更完整”不是无边界地读取一切，而是能够识别当前决定缺少什么，并沿着真实来源补齐关键上下文：

- 区分用户意图、业务语义、架构契约、代码现状、运行证据和历史结论；
- 找到 source of truth、owner、生产者到消费者的调用链和受影响路径；
- 看见矛盾、未知和证据边界，不把推测伪装成事实；
- 用渐进披露控制成本，只读取会改变下一步判断的信息。

SBA 应持续增强 Agent 建立“足够完整决策视图”的能力，而不是单纯扩大上下文窗口或堆积文档。

### 2. 在没有标准答案时做判断

真实工作经常没有唯一正确答案。Agent 不能只等待规则命中或照抄已有方案，它需要：

- 明确目标、约束、未知和完成证据；
- 区分事实判断、风险判断、产品取舍和权限边界；
- 提出真正不同的方案，说明收益、代价、可逆性和残余风险；
- 在证据足够时选择方向并推进，在缺少承重语义时准确地请求最小澄清；
- 新证据推翻前提时主动重排路径，而不是维护原计划的表面完整。

SBA 提供的是判断支架，不是用更多流程替 Agent 做决定。

新证据推翻承重结论时，不得静默覆盖；必须重新检查方案、验收、边界和 Task Anchor。涉及规范性业务判断时，由业务 owner 确认。

> 代码可以暴露约束、成本和风险，但无权替用户修改已经确认的业务主线。发现偏移必须立即停下来协商，不能静默妥协，也不能拖到最后补报。

### 3. 让别人按照你的意愿做事情

这里的“意愿”不是操控，也不是让所有工作都经过一个中心，而是把目标变成其他 Agent、工具和协作者能够可靠执行的共同契约：

- 定义标准、角色、owner、输入、输出、禁止区和验收方式；
- 把独立工作交给合适的执行者，同时保留主线判断和最终复核；
- 让上下文来源、变更范围、验证证据和剩余风险可追踪；
- 协调冲突与资源，拒绝局部完成冒充整体结果；
- 用复核和反馈修正偏差，最终带出可验证的结果。

SBA 要让 Agent 从“自己执行得很快”进化到“能够组织可靠执行”。

## 真正的不可替代

> 真正的不可替代，不是让所有的东西都经过你，而是当信息不完整、资源不够、需求不清晰的时候，你能判断方向。

不可替代来自判断，而不是垄断流程。一个必须亲自处理所有任务、掌握所有细节才能工作的 Agent，只是瓶颈；一个能够在不确定条件下找到方向、划清边界、组织执行并对结果负责的 Agent，才具有杠杆。

> 如果你能定义标准、判断风险、协调资源、带出结果，你就不是一个执行者，你开始变成一个更大的入口。

“更大的入口”意味着更多问题可以经由它被澄清、拆解、组织和闭环，不意味着更多动作必须由它亲自完成。

## 不可妥协的原则

1. **新机制必须减少责任或解决真实失败，不能只是让架构显得完整。**
2. **默认核心应该更小但完整，而不是依赖用户理解“装哪些、不装哪些”。**
3. **规则必须能被正确激活；仅仅存进仓库不算产生价值。**
4. **Agent 的结论必须可复核：来源、边界、owner、验证契约都要清楚。**
5. **语义完整性优先于代码改动最少，但验证成本必须与风险匹配。验证前必须把风险、验证证据和停止条件绑定起来，不得用测试数量代替证据质量。**
6. **跨 harness 兼容应当优雅降级，不能让某个工具的限制污染整体产品模型。**
7. **SBA 负责吸收工程复杂度，用户只承担真正属于产品和业务的决策。**
8. **局部可行动性与单一语义所有权必须同时成立。** 触发条件、立即动作、当前任务的验收责任可以适度重复；完整定义、状态转换和多步骤流程原则上只维护一次。例外必须能证明完整重复比跳转、加载或生成更便宜。是否保留局部重复，由 Agent 结合真实任务路径、漂移后果、读取与跳转成本和生成成本判断；不得机械地“一律抽取”，也不得默认手工复制完整规则或完整流程。
9. **路由只确定第一个工作流，知识由工作流依据证据渐进拉取。** 路由阶段不得把“可能相关”当成“当前必需”并预装完整知识包；工作流应围绕尚未解决、且会改变下一步动作的判断，按需读取规则、参考资料和业务模型。工作流选定以后，源码定位也可以按证据逐层选择技术知识；前两阶段不读取源码正文，但允许在当前判断需要时读取一个紧凑、已路由的技术地图来缩小 owner、路径或 symbol 候选。技术地图是可选加速器：存在且被证据激活时可以减少无关搜索；不存在或未被激活时，Agent 仍必须依靠目录、文件名、确定性搜索和源码证据完成完整定位。技术地图默认是当前 Session 中随定位证据逐步维护的临时状态，不在用户仓库持久化；持久技术地图是少数真实压力触发的例外，必须单独通过记录价值、行动激活和后续维护判断。从宽泛意义上说，Task Anchor 也是一种任务状态地图，但在 SBA 的正式术语中不得把它称为技术地图：Task Anchor 是管理 Goal、Done When 和 Boundaries 的任务级容器，运行时定位地图只是其中当前定位步骤的证据子状态，二者是包含关系而不是同义词。Task 路由与领域选择是由证据隔开的两个阶段：业务 overlay 不得仅凭关键词前置加载，只有最小证据表明当前判断确实依赖业务语义时才延迟绑定。物理拆分 task routing 与领域目录，只是大型业务项目在领域目录具备独立加载理由时落实该时间边界的手段，不是默认结构要求；没有独立加载时机，就不得为了目录整齐而拆文件。
10. **执行围绕一条面向结果、允许回退的主线展开：用户输入 → 拆解 → 定位 → 实现 → 验证 → 条件沉淀 → 交付。** 这是一条生命周期主线，不是要求所有任务机械走完的固定仪式；简单任务、只读任务和无需形成持久知识的任务可以跳过不适用阶段。主步骤必须产生能够改变下一步判断或被下一阶段消费的证据；执行过命令、生成了文件或获得成功退出码，本身不构成阶段完成。证据失败或前提变化时，应回到定位或拆解，而不是为了维持线性进度继续执行。验证不是一次性节点：沉淀如果改变规则、工作流、路由或其他交付内容，必须再次验证。交付是结果出口，可能是结论、提交、推送、MR、部署或其他约定产物，具体动作受任务工作流和用户授权约束。
11. **Plan 的逻辑覆盖与物理材料化必须分离。** Plan 只有在脱离父 Plan 后无法独立完成、冻结和直接消费时，才是 `subplan_of` 并物理嵌套；否则保持独立，由 Integrating Plan 使用单向 `consumes` 关系组合。先区分用户要形成/更新具体 Plan，还是只要方法说明、现有 Plan 审查或方向头脑风暴；后者只取足以支持判断的代表性证据，不执行完整规划。复杂度只决定分析深度，不决定是否创建文件；需求、Current → Target、领域、数据、契约、影响、风险和验证等维度，由当前证据是否改变设计来激活。每次只围绕当前承重问题取证；证据一旦能够解决或推翻该问题，或定位下一个语义 owner，就停止扩读，疑似消费者、风险和相邻流程只进入候选队列，不能自动变成整仓读取义务。已有 Plan 存在多个 Open Questions 时，先选择影响最大的一个，只读取能够表述或解决它的证据，其余问题和证据路径在轮到之前保持未打开。交互式 Complex/Large 规划在第一个 Design Slice 暴露由用户决定的规范性选择或高影响假设后，必须先讨论这一件事，再打开无关 Slice；只有用户明确要求一次性完整产物时才连续展开。默认先在会话和 harness Native Plan 中推进，只有用户明确需要持久产物，或分析中出现上下文保真、实现交接、独立消费/评审/验证/生命周期、模块间冲突等真实承载压力时，才创建当前最小 artifact。首个文件与每个后续 sibling 都必须独立证明它会改变决策、任务边界、风险处理或验证，不得从 Complex/Large 标签、固定阶段、文件数或章节完整性反推建档。
12. **语义翻译与实现绑定由同一运行时 Change Contract 贯通。** 语义翻译属于“拆解”，源码词汇扩展与 owner 证明属于“定位”；二者由一份运行时 Change Contract 连起来，不新增顶层阶段、不预置全局关键词词典、不强制持久 Wiki、不把推测升级为 authority。推测用于生成候选；证据用于缩小和推翻候选；可追溯的 desired-meaning authority 决定规范性范围；当前源码证据绑定实现事实。只有规范性含义、权限边界和高代价取舍等真正属于用户的硬关卡才请求决策；文件、类、搜索词、当前 owner 等 Agent 能从仓库获得的技术事实不得转交用户。该契约不由 PRD、Figma、关键词、任务大小或固定流程触发，也不对所有任务强制执行；首个工作流选定后，只有当前语义契约不足以安全进入定位或修改，且缺失可能改变范围、authority、保留行为或验收时才展开。明确请求、已确认 Plan、清晰的 observed/expected contract 或已路由 owner 已经提供足够语义时，直接复用并走快路径。契约默认作为当前 Session 的内部状态运行，只在需要用户硬关卡决策、结论无法复核或用户明确要求审计时展示紧凑检查点。
13. **第一次已经证明、且能改变未来动作的失败经验，必须在修复被 red-to-green 证据确认后立即写回正确 owner 并接入下一次动作。** 不等待第二次复发，不拖到最终 AAR，也不先写进错误日志、候选账本或新的 Memory 子系统。未证实的假设、同一未解决任务里的重试、一次性命令错误和没有稳定预防动作的瞬时外部失败只保留在当前 Session。后续独立复发先检查已有知识是否在错误动作之前被命中并真正改变了动作：没有命中就修激活，命中后仍失败才在现有权限边界内加强可执行预防；复发本身不扩大提交、推送、MR、部署、数据库、团队规则或外部系统权限。
14. **完整流程只有在至少两次独立完成后，才应在交付完成边界被主动提炼并询问是否固化。** 身份来自共同目标、有序阶段、输入输出、集成验收和权限关卡，不来自命令相似、同一任务或未完成重试。Agent 先检查现有 owner，给出一个 `extend`、纯 `compose` 或 `create` 判断；纯组合没有持久缺口时不提案。提案必须排在 `Closure Complete` 的结果报告之后，拒绝或暂缓不创建候选记录，同一 Session 不重复追问。接受后才进入新路由任务，沿真实 provenance 只修改 canonical owner，并完成下游装配/安装与验证；跨仓流程只有一个完整编排 owner，其余位置保留薄 hook。Workflow 接受不扩大提交、推送、MR、部署、数据库、工单、版本、评审人、发布或合并权限。

## 发展方向

SBA 的演进优先服务以下方向：

1. **更完整但更克制的上下文**：增强业务语义、owner、调用关系、context provenance 和证据边界，同时减少无关读取。
2. **更强的模糊判断能力**：让 Agent 能在目标冲突、证据不足和无标准答案时给出有依据的方向，而不是机械执行最近的规则。
3. **更可靠的协作与委派**：通过结构化契约、能力边界、防递归、主 Agent 复核和结果整合，放大执行能力但不放弃责任。
4. **更低的普通用户成本**：优先删除、合并和内化复杂度；每增加一个用户可见概念，都要证明它不能由系统吸收。
5. **更安全的生命周期**：让项目知识、上游机制、生成内容和运行数据各归其主，更新可比较、可验证、可回退。
6. **从执行工具走向结果入口**：逐步具备定义标准、判断风险、协调资源和带出结果的能力，但不发展成必须承接所有工作的中心化平台。

## 明确不走的方向

- 不发展成 Agent 操作系统、任务数据库或项目管理平台；
- 不为了“以后也许有用”持续增加文件、状态、marker、脚本和术语；
- 不用结构检查的绿色结果冒充语义正确；
- 不因为外部项目设计漂亮就直接吸收，必须经过真实痛点和净收益验证；
- 不让所有事情经过主 Agent 来证明其重要性，能通过标准和契约可靠分发的工作应当分发；
- 不把维护者的安装、组合、升级和选择责任转嫁给普通使用者。

## 方向决策检查

任何重大新机制、默认行为或产品方向，在进入实现前都应回答：

1. 它让 Agent 更能看全信息、做出判断或组织别人带出结果了吗？
2. 它减少了普通使用者的责任，还是只是把作者复杂度换了一个名字交给用户？
3. 它解决的是已经出现的痛点，还是为了想象中的完整性增加机制？
4. 它的 owner、激活路径、验证契约和退出方式是否清楚？
5. 没有它时更轻的方案为什么不够？加入它后又能删除或内化什么？
6. 它是在扩大 SBA 的判断与协调杠杆，还是在制造新的中心化瓶颈？

答不清这些问题，默认不进入 SBA。

## 如何使用这份圣经

- SBA 自身进行产品定位、发展方向、外部能力吸收或重大机制设计时，先读取本文件，再进入方案规划。
- 具体 Plan 可以提出未来目标；只有实现、验证和文档同步落地后，才算成为当前产品能力。
- 本文件应保持稳定。改变最高纲领、三项能力或不可替代性的定义，必须由产品 owner 明确确认。
- 它不进入下游模板，不成为普通任务的 Always Read，也不替代更具体的规则和工作流。
